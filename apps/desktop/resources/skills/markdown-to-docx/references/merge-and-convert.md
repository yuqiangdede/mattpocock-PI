# 合并组件文档并转 Word

## 收集与融合

开始前让用户提供组件 MD 的路径/附件、产品范围、最终文档类型、**人工指定的最终文档名称**，以及 Word 模板或推荐格式选择。沿用当前会话已明确的值；缺少名称或格式选择时先询问，不能自行命名或默认接受推荐项。模板读取失败不静默改用默认格式。

推荐用户选择：正式交付版 formal（推荐）、评审协作版 review、企业简洁版 compact；具体差异及需求/设计章节结构见 [component-doc-merge 格式说明](../../component-doc-merge/references/intake-and-format.md)。可上传 .doc/.docx 模板；旧格式实际转换后读取，不改后缀伪装。

读取并执行 [component-doc-merge](../../component-doc-merge/SKILL.md)，只执行输入核对、产品级融合、Markdown 制作与校审。它负责去重、互补规则、冲突处理、跨组件业务/工程链路、统一编号与资产；不要将多个 MD 直接传给 Pandoc 并称为产品级融合。该技能不可用时停止合并分支，说明缺少哪一能力，保留原稿；已有单文件转换仍可执行。

合并默认不重新扫描源码，也不把输入中提到的其他组件自动加入范围。需求与设计分开融合；用户要两种则人工指定两份名称，分别完成同名 MD/Word。

## 转换交接

接收融合结果时标明“融合已完成，仅转换此单一 MD”，直接执行当前技能的单文件转换阶段，避免循环。沿用用户指定的标题、文件名、输出目录、模板/格式、图形资产和已确认缺口策略。

推荐格式示例（名称必须换成用户实际指定值）：

```powershell
python "<skill>/scripts/convert.py" "合并成果/产品需求规格说明书.md" "合并成果/产品需求规格说明书.docx" --profile formal --title "产品需求规格说明书"
```

模板示例：

```powershell
python "<skill>/scripts/convert.py" "合并成果/产品总体设计说明书.md" "合并成果/产品总体设计说明书.docx" --reference-doc "参考/模板.docx" --toc
```

脚本仅转换单一已融合 MD，不自动做语义合并。reference-doc 不保留模板正文；需要企业固定封面或页眉页脚字段时按格式说明专项制作，核对页码和实际布局。

## 完成交付

按 [verification.md](verification.md) 分别核对“融合 MD 对全部组件输入的完整性”与“Word 对融合 MD 的内容一致性”，不要只对最终 Word 做结构检查。标题、文件名主干及目录、术语、表格、图号、公式、Mermaid/图表与最终正文一致。

交付 `<人工指定名称>.md`、必要 assets 和同名 `.docx`；内部映射、AST、缓存及 QA 不混入正式文档。标准文档指用户选定的格式及正确结构，不宣称自动满足某个国家/行业标准。若用户明确要求旧 `.doc`，在 DOCX 成功后通过已有兼容工具另存、检查并交付；缺工具时明确旧格式未完成。

合并成功但转换失败时保留融合 MD、资产和用户选择，说明 Word 的具体阻塞；修复转换后继续，不重做已确认的融合或改变原输入。
