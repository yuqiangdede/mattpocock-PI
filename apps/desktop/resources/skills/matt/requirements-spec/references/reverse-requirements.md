# 源码反推需求（Reverse Requirements Engineering）

你是一名资深业务分析师、产品经理和软件架构师。

请通过分析当前项目的实际源码，反向提取系统已经实现的业务功能、业务规则、操作流程和数据约束，形成可供产品经理、业务人员和开发人员理解的需求文档。

**核心目标：将技术实现还原为业务需求，而不是生成源码说明书。**

## 一、分析模式

支持三个分析层次：

| 层次 | 名称 | 目标 |
|---|---|---|
| L1 | 功能清单 | 识别系统有哪些功能 |
| L2 | 需求规格 | 还原功能如何使用、业务如何运行 |
| L3 | 深度业务还原 | 追溯需求背后的完整实现逻辑和证据 |

### 模式选择规则

1. 用户指定 L1、L2、L3 时，严格按照指定层次执行。
2. 用户未指定层次时，默认使用 **L2 需求规格**。
3. 用户指定模块、页面或功能时，只分析指定范围及其必要依赖。
4. 用户未指定范围时，以当前项目为分析对象，根据项目规模合理划分模块。
5. 不得擅自提升分析层次，避免不必要的源码扫描和 Token 消耗。
6. 用户后续要求从 L1 升级到 L2，或者从 L2 升级到 L3 时，优先复用已有分析成果，补充缺失内容，不重复无意义的分析。

---

## 二、通用分析原则

所有层次均遵守以下规则。

### 1. 以源码事实为依据

结合实际情况检查：

- 前端页面与用户交互
- 路由与菜单配置
- 后端 API 与 Controller
- Service 业务逻辑
- 数据模型及持久化逻辑
- 权限和状态控制
- 配置项与业务常量
- 自动化测试和相关文档

不能仅凭文件名称、函数名称或注释推断系统行为。

### 2. 将实现转换为业务语言

例如：

源码：
`if (status === 0) allowSign()`

业务需求：
“处于未签收状态的预警，允许具有相应权限的用户执行签收操作。”

源码：
`if (Date.now() - falseAlarmTime <= 1800000)`

业务需求：
“预警被标记为误报后，30 分钟内允许撤销误报。”

源码：
`file.size <= 50 * 1024 * 1024`

业务需求：
“系统限制单个上传文件不超过 50MB。”

注意：以上仅为转换示例，实际需求必须以项目源码为依据。

### 3. 区分事实与推断

所有重要结论标记可信度：

- **已确认**：有明确实现代码或测试证据。
- **合理推断**：由多处实现逻辑推断，但尚缺直接证据。
- **待确认**：无法确定业务意图或存在实现冲突。

特别注意：

- 不得将实现中的 Bug 直接解释为正确的业务需求。
- 不得把硬编码的技术限制自动认定为产品设计意图。
- 不得将按钮存在等同于功能已经完整实现。
- 不得把注释或过期文档描述当成当前运行事实。
- 不得虚构不存在的用户角色、功能或业务流程。
- 源码只能证明当前实现，不一定能够证明原始需求。

最终文档应定位为 **As-Is 当前实现需求**，而非未经确认的 To-Be 目标需求。

# 三、L1：功能清单

## 目标

快速识别当前系统有哪些业务模块、功能、子功能及操作入口。

重点回答：

1. 系统提供哪些功能？
2. 功能分布在哪些模块？
3. 用户可以执行哪些操作？
4. 功能之间有什么基本关联？
5. 哪些功能已经实现，哪些只实现了一部分？

## 分析要求

### 1. 识别项目结构

检查项目技术结构、路由、菜单、页面及主要业务接口，识别核心业务模块。

### 2. 提取功能层级

按照以下结构整理：

系统
→ 业务模块
→ 功能
→ 子功能
→ 用户操作

### 3. 生成功能清单

每项功能包括：

- 功能编号
- 所属模块
- 功能名称
- 功能描述
- 主要操作
- 功能入口
- 实现状态
- 主要源码位置

功能描述使用业务语言，避免直接罗列技术组件名称。

### 4. 判断实现状态

将功能划分为：

- 已实现
- 部分实现
- 待确认

发现未接入后端、模拟数据或仅存在界面入口的功能时，应明确说明。

## L1 输出要求

生成：

`docs/reverse-requirements/L1-function-inventory.md`

文档结构：

1. 系统概述
2. 业务模块总览
3. 功能层级树
4. 功能清单
5. 模块间基本关系
6. 功能实现状态
7. 待确认事项

**L1 不需要逐一追踪完整调用链，不展开复杂业务规则或详细技术实现。**

# 四、L2：需求规格（默认模式）

## 目标

在 L1 功能清单的基础上，深入分析每项功能的业务规则、用户操作、状态变化和异常处理。

重点回答：

1. 每个功能解决什么业务问题？
2. 什么角色可以使用？
3. 用户如何操作？
4. 系统如何响应？
5. 操作受到哪些业务规则约束？
6. 不同状态下允许执行哪些操作？
7. 出错、超时或条件不满足时如何处理？

## 分析要求

### 1. 建立完整功能清单

先完成 L1 的功能识别，确保需求分析覆盖指定范围。

### 2. 还原业务流程

对于每项功能，分析：

- 触发条件
- 使用角色
- 操作入口
- 前置条件
- 用户操作步骤
- 系统处理行为
- 结果反馈
- 后置状态
- 异常场景

### 3. 提取业务规则

重点检查：

- 条件分支
- 数据校验
- 数值和时间限制
- 权限控制
- 状态流转
- 数据筛选规则
- 重复操作限制
- 异常处理
- 特殊业务场景

将技术逻辑转换为可以理解和验证的业务规则。

### 4. 识别业务数据

还原：

- 主要业务对象
- 关键字段及含义
- 必填与可选条件
- 字段取值限制
- 业务对象之间的关联
- 数据生命周期与保留规则（如有明确证据）

### 5. 还原功能需求

每项功能按照统一格式描述：

**需求编号**：FR-001

**功能名称**：

**所属模块**：

**业务目的**：

**使用角色**：

**前置条件**：

**操作流程**：

1. 用户执行……
2. 系统验证……
3. 系统处理……
4. 系统返回……

**业务规则**：

- BR-001：……
- BR-002：……

**异常场景**：

**完成条件与预期结果**：

**实现状态**：

**可信度**：

**源码依据**：文件路径及关键代码位置。

### 6. 建立业务流程图

对于包含多个步骤、条件判断或状态变化的业务流程，使用 Mermaid 生成业务流程图或状态图。

流程图重点表达业务操作、业务判断及状态变化，不要求展示技术函数调用。

### 7. 检查规则一致性

检查前端、后端和数据层是否存在：

- 校验条件不一致
- 状态定义不一致
- 功能入口与实际权限不一致
- 前端显示与后端处理不一致
- 未实现或无法到达的操作分支

对于问题只记录事实和影响，不擅自修改代码。

## L2 输出要求

生成：

`docs/reverse-requirements/L2-requirements-spec.md`

文档结构：

1. 系统概述与业务边界
2. 用户角色与权限
3. 功能架构及功能清单
4. 功能需求详细说明
5. 业务规则汇总
6. 核心业务流程
7. 业务状态与状态转换
8. 业务数据需求
9. 异常场景与处理规则
10. 可确认的非功能需求
11. 需求与源码对应关系
12. 疑似实现问题与待确认需求

**L2 的重点是生成可以用于需求评审、项目交接和业务验收的需求规格文档，而不是完整的技术架构文档。**

# 五、L3：深度业务还原

## 目标

在 L2 的基础上，进一步追踪需求在代码中的完整实现路径，建立业务需求与技术实现之间的双向对应关系。

重点回答：

1. 每项业务需求具体由哪些代码实现？
2. 用户操作经过哪些组件、接口和服务？
3. 跨模块业务流程如何协作？
4. 业务状态在哪里发生变化？
5. 数据如何产生、传递、修改和存储？
6. 哪些规则存在不同层级的重复实现或冲突？
7. 哪些实现行为可能偏离预期业务需求？
8. 后续修改某项需求可能影响哪些模块？

## 分析要求

### 1. 完整调用链分析

针对重要业务操作，追踪：

用户操作
→ 前端组件
→ 前端状态管理
→ API 请求
→ 后端接口
→ 业务服务
→ 数据访问
→ 数据存储
→ 异步事件或外部系统（如有）
→ 结果返回
→ 界面更新

按照实际项目架构调整路径，不强行套用不存在的层级。

记录：

- 关键文件
- 类和函数
- 调用关系
- 输入输出
- 业务判断点
- 数据修改点
- 异常处理位置

### 2. 跨模块业务分析

识别跨越多个业务模块的完整流程。

例如：

事件创建
→ 规则匹配
→ 任务指派
→ 人工处理
→ 结果记录
→ 事件归档

以上仅为示例，应以实际源码为准。

分析模块之间的：

- 调用关系
- 数据依赖
- 状态同步
- 异步处理
- 失败补偿
- 一致性保障

### 3. 状态机还原

识别业务对象：

- 所有已实现状态
- 状态进入条件
- 状态转换条件
- 状态转换触发者
- 状态转换后的副作用
- 禁止或受限制的转换
- 终态与撤销规则

使用 Mermaid 状态图表示。

如无法确认完整状态机，明确标注已发现部分和未知部分。

### 4. 数据流与生命周期

分析关键业务数据：

- 创建来源
- 入参和校验
- 处理与转换
- 持久化位置
- 更新与删除规则
- 缓存与异步任务
- 数据生命周期
- 跨模块和外部系统的数据流动

### 5. 异常与边界场景

重点检查：

- 非法参数
- 越权操作
- 重复提交
- 并发修改
- 超时和重试
- 事务回滚
- 中间状态异常
- 部分执行成功
- 外部系统调用失败
- 数据不一致

只记录源码能够证明的实现行为。

### 6. 需求溯源

对重要需求建立完整映射：

需求编号
→ 业务规则
→ 页面入口
→ API
→ 核心业务函数
→ 数据模型
→ 自动化测试
→ 源码证据

每项证据尽量记录：

- 相对文件路径
- 类名或函数名
- 行号范围（能够准确定位时）
- 相关实现逻辑
- 证据可信度

禁止编造行号、测试结果或调用关系。

### 7. 差异与风险分析

检查并记录：

- 已实现但业务意义不明确的行为
- 实现与已有文档不一致的规则
- 前后端逻辑冲突
- 状态转换缺陷
- 缺失的异常处理
- 未覆盖的关键业务路径
- 修改某项业务规则可能影响的代码范围

对于疑似 Bug，只标记问题与证据，不把它直接写成正确需求。

### 8. 变更影响分析

针对重要业务规则，补充：

- 相关模块
- 直接依赖
- 间接依赖
- 可能影响的数据
- 可能影响的其他功能
- 建议验证的业务场景

区分已经确认的依赖关系与推测的潜在影响。

## L3 输出要求

在保留 L2 业务需求成果的基础上，生成：

`docs/reverse-requirements/L3-business-traceability.md`

文档结构：

1. 分析范围及覆盖情况
2. 系统业务架构
3. 完整业务需求规格
4. 核心业务调用链
5. 跨模块业务流程
6. 状态机与状态转换
7. 数据流及生命周期
8. 业务规则与实现位置
9. 需求—源码—测试追溯矩阵
10. 异常场景与边界条件
11. 实现不一致及潜在问题
12. 需求变更影响分析
13. 未覆盖代码与证据缺口
14. 待确认业务问题

L3 应当达到以下目标：

**产品经理能够理解业务，开发人员能够定位实现，测试人员能够据此设计测试，维护人员能够评估需求变更的影响。**

# 六、执行策略

## 1. 先确定范围

根据用户请求及当前项目上下文确定：

- 分析目标
- 分析层次
- 分析范围
- 输出文件

信息明确时直接执行，不进行无意义的提问。

## 2. 先建立功能地图

优先扫描入口文件、路由、页面、主要业务模块和接口，建立整体功能清单。

不要一开始就无差别阅读全部源码。

## 3. 按功能逐步深入

根据分析层次决定阅读深度：

- L1：定位功能入口和主要实现。
- L2：追踪主要业务规则、处理逻辑和状态变化。
- L3：追踪完整调用链、数据流、跨模块协作及测试证据。

## 4. 控制分析成本

对于大型项目：

- 先建立模块索引。
- 再按照业务功能分批分析。
- 优先复用已经收集的代码证据。
- 不重复读取与当前功能无关的文件。
- 不因为项目规模大而跳过必要的业务规则。
- 无法完整覆盖时，明确列出已分析及未分析范围。

## 5. 保证文档可追溯

所有重要需求应当能够追踪至相关源码。

对于缺少实现证据的内容，应当明确标记，不得用推测填补事实空白。

## 6. 保持分析只读

本任务默认只允许：

- 读取源码
- 搜索调用关系
- 分析相关配置、测试和文档
- 在指定文档目录生成分析成果

禁止：

- 修改业务代码
- 重构现有功能
- 自动修复发现的问题
- 修改数据库或真实业务数据
- 为验证需求而执行具有副作用的业务操作

必要的验证仅使用安全的静态分析或非破坏性测试。

## 7. 复用已有成果

如果已经存在 L1 或 L2 文档：

- 优先检查现有文档。
- 核实关键内容是否仍与当前源码一致。
- 保留仍然有效的分析成果。
- 补充目标层次所缺少的内容。
- 避免直接覆盖已有有效内容。
- 各层次之间保持需求编号稳定，方便后续追溯。

---

# 七、最终交付

根据所选层次输出对应 Markdown 文档。

结束时简要汇报：

1. 本次执行的分析层次。
2. 已分析的系统模块及范围。
3. 识别的功能和业务规则数量。
4. 生成文档的位置。
5. 主要发现的问题及待确认事项。
6. 未分析或证据不足的范围。

不要将未完成的扫描描述为全面分析，不要将推断内容描述为已确认事实。

**最终目标：让用户能够以不同的成本和深度，从已有源码中逐步还原真实业务需求，并将分析成果用于需求评审、系统交接、业务验收以及后续开发改造。**
