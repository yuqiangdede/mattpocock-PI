# 组件文档融合

配合“逐组件编制 Markdown，再融合并转 Word”的工作流。以产品、用户场景和整体业务目标组织一份完整文档；组件是实现能力的协作方，不是最终需求的一级目录。需求融合与设计融合分别执行，不把两种正文混成一份。

## 1 收集输入后开始

先按 [references/intake-and-format.md](references/intake-and-format.md) 收集并核对：

- 本次纳入的组件文档路径/附件及产品范围，明确是需求、总体设计或概要设计；已有明确类型直接沿用。
- **用户人工指定的最终文档名称**。封面标题、Markdown 一级标题、MD 与后续 Word 文件名主干保持一致；未指定时必须询问，不自行采用“合并文档”或按组件名拼接名称。
- **用户的格式选择**：提供 Word 模板，或在推荐格式中明确选择一个。模板可为 .doc/.docx，按实际兼容工具读取；未回答不等于采用推荐项。

一次收齐，不重复询问已有明确输入。缺项时仅收集与核对材料，不开始内容提取、融合或生成正式文档。默认以已有组件文档为依据，不要求重新提供源码路径；只有用户另行要求源码核对时才收集源码，不自动重新启动需求/设计编制 skill。

## 2 产品级融合

读取 [references/merge-rules.md](references/merge-rules.md)，建立组件输入到产品能力/设计的映射，逐项处理纳入、合并、拆分、差异、排除及冲突。先明确整体范围与业务链路，再重新编写正文；不按输入文件顺序粘贴，也不只统一标题或删除来源字段。

需求分支围绕谁在什么场景解决什么问题、产品提供什么能力和可观察结果。设计分支从产品能力和端到端场景说明整体架构、协作、数据和失败处理，同时保留真实组件、接口和部署边界。以产品维度组织设计不等于把技术设计改成需求描述。

冲突先核对版本、范围与已有决定。会改变权限、金额、状态结果、数据权威归属、接口承诺及验收指标的冲突，展示具体选项与影响并取得明确决定；其他可保留准确缺口，不能补造组件之间不存在的协作关系。用户已选的待确认处理策略沿用。

## 3 制作统一 Markdown

按选定结构与样式参考生成 `<人工指定名称>.md`。用户给出输出目录时沿用，否则使用本次输入文档的共同父目录下 `合并成果/`；多个目录没有明确共同业务目录时先询问输出位置，不保存到技能目录。不覆盖原输入或无关文件。

统一概述、范围、角色、术语、需求/设计标识、图表编号及跨节引用。最终正文移除来源索引、源码路径、可信度和合并过程；有效设计理由、版本差异、业务分类及真实缺口保留。映射与决策记录放到该输出目录的 `.merge-work/`，不混入正式正文。

图片按原文件所在目录解析，复制至 `assets/<文档名称>/` 下互不覆盖的命名空间，更新合并稿内的相对路径；检查同名图片、参考式图片链接、脚注及标题锚点冲突。Mermaid/图表源保留可维护代码块，统一命名与正文语义，不凭空改数据。合并 MD 脱离原目录后仍能携带资产阅读。

## 4 校审与交接

Before delivery or Word conversion, run the final chapter-title audit defined in [references/merge-rules.md](references/merge-rules.md#final-chapter-title-audit). Resolve accidental duplicate headings and recheck the revised document before handoff.

按 merge-rules.md 的完成条件检查全量输入映射、产品能力覆盖、跨组件正常/异常链路、编号、图文及资产。没有读过的材料不能声称已融合；没有实际证据时不声明功能或部署已验证。

本技能的内容产物为统一 Markdown 与必要资产，同时保留用户选择的模板/格式用于后续 Word。用户同时要求 Word，或由 `$markdown-to-docx` 的合并入口调用时，将已校审 MD、人工名称、模板路径/格式标识与输出位置一次性交给转换流程，继续完成 DOCX，不停在“可以再转换”的建议上。

为避免循环，交接标明“融合已完成，仅转换此单一 MD”，转换技能不再调用合并。若单独请求合并 Markdown，则交付 MD 即结束；转换工具缺失时保留融合稿并明确 Word 尚未完成。文档生成不授权提交代码或发布文件。

## 执行效率与增量检查

保留上述名称、模板/格式选择、融合、校审和交接流程。复用已回答的选择、输入版本、条目映射及图形资产清单；文档无变化时不重复提取，输入变化时更新受影响映射与跨组件链路。

按需一次提取每份输入的结构、正文、表格、图形及资源引用，保存精确 UTF-8 文本。乱码先解决再匹配；自动删除或替换核对目标唯一性与实际数量，不能因未命中而跳过输入条目。

融合前确定本次验收项：输入处理去向、重复合并、必要差异、编号引用及资产完整性。复用同一清单或脚本，修订后复查关联内容，交付前仍执行既有整体校审。Word 转换失败时保留已校审融合稿和交接记录，仅重试失败阶段；内容或输入变化时才回到对应融合步骤。

## 调用示例

> 使用 $component-doc-merge 合并这些组件需求 MD。先让我指定最终文档名称，再让我提供 Word 模板或选择推荐格式；按产品能力融合全部组件及跨组件流程，然后用 markdown-to-docx 转为同名 Word。

## 执行补充：大规模融合与中断安全

按[公共文档安全写入及恢复约定](../_shared/README.md)执行，但人工指定文档名、选择格式和冲突决策仍遵守本技能前述规则。

- 输入多时先逐文件提取结构、业务条目、编号与资产映射，输出短的结构化证据索引；需要融合判断的跨组件职责、冲突、流程和产品术语仍由主代理统筹，不因上下文不足跳过某份原始文件。
- 根据最终产品级章节建立所有输入条目去向及预计章节清单，大文件先生成章节 part，再用 document_workspace.py 检查每个必需标题恰好一次并原子组装，避免一次性写入 100KB+ 和用 Edit 追加整章。
- **任何中断/外部编辑之后**都要检查目标现有大小、行数、指纹、首尾、已完成章节和来源映射，重新判断是否需要追加；不得直接依照旧摘要写入或无条件生成新快照覆盖冲突。
- 融合 MD 定稿后运行 document_qa.py，再按原有合并映射与交接规则验证完整性；转 Word 后可用 docx_text_check.py 核对关键标题/术语，不能仅用 OOXML 文本片段直接匹配来判定缺失。
- **机械搬运与语义融合分开**：源文件章节切片、编号规则化与有边界的拼接用确定性脚本并核对处理数量，不交给子代理逐段 Edit；组件职责冲突、重复能力归并及产品级业务链路仍由主 Agent 处理。各 part 按完整产品章节组织，组装后独立对比预期章节**顺序/数量**与输入条目去向，不能只检查标题存在。
- 多步骤交接在 scratch 保留输入指纹、用户选择、组件映射、已验证 MD 和实际 DOCX 阶段状态；按 _shared 检查点恢复。DOCX 失败时不得重新融合或丢弃已校审 MD；不存在的跨组件协作不因需要成文而补造。
