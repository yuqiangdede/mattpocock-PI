# 概要设计内容模板与校审

用户模板优先；无模板采用以下结构并按范围裁剪。模块按职责划分，接口与数据按业务语义描述，不把源码目录和类列表换名为概要设计。

## 建议目录

1. 引言：目的、读者、需求版本、可选总体设计基准、术语及约定。
2. 设计范围与架构约束：模块范围、总体方案衔接、环境、依赖与关键限制。
3. 模块划分与协作：模块职责、输入输出、边界、依赖及需求分配。
4. 核心业务处理设计：关键场景、触发、交互、处理、结果、异常及恢复。
5. 接口设计：模块间及外部关键接口、契约、鉴权、返回、超时/重试/幂等及兼容。
6. 数据与状态设计：逻辑对象、关键数据约束、归属、关联、生命周期、状态及转换。
7. 异常与一致性设计：事务、并发、重复、异步、部分成功、补偿和外部依赖失败。
8. 安全及质量设计：权限落实、数据隔离、日志审计、可观测性、性能与可靠性机制。
9. 变更衔接与验证：新增/调整/复用、兼容与迁移、受影响模块及关键验证场景。
10. 需求覆盖与未决事项：需求到模块、接口、流程及数据的覆盖摘要与待确认问题。

总体架构只简述约束，不重复整个总体方案。核心处理可按模块或跨模块业务场景组织，选择一种主结构，避免同一流程在多章重复。

## 模块设计卡

每个重要模块按以下字段展开；小模块可合表，确实不适用的项说明原因：

模块表之前可参考已有文档的总体说明写法，先叙述模块定位、业务目的、主要能力、职责边界和协作结果，再展开契约和处理机制。用当前模块事实填充，统一文风及详略，不照搬其他项目的功能或凭接口名猜业务。

| 字段 | 编制内容 |
| --- | --- |
| 模块标识与名称 | 稳定标识、明确职责名称，与图中名称一致 |
| 职责与边界 | 承担的业务/运行职责及由其他模块负责的边界 |
| 关联需求 | 有效需求编号和质量约束，不凭空添加业务能力 |
| 输入与触发 | 用户、接口、消息、调度或事件，数据及前置条件 |
| 输出与结果 | 返回、事件、通知、数据/状态变化及完成语义 |
| 依赖与数据归属 | 调用模块、外部依赖、权威数据和访问职责 |
| 主要处理 | 校验、权限、规则、协作、数据变更和结果顺序 |
| 失败与恢复 | 失败条件、保留/回滚/重试/补偿及人工介入边界 |
| 验证场景 | 可观察的正常、边界及关键异常结果 |

这里描述设计机制，不能只复制需求中的“系统应支持”。例如需求要求避免重复处理，设计需说明去重键/幂等条件、控制位置、有效范围及失败恢复，而不是无依据地指定某个现成类。

## 关键接口契约

| 字段 | 编制内容 |
| --- | --- |
| 接口标识/名称 | 稳定标识、目的、提供方与调用方 |
| 类型与触发 | 同步调用、异步事件、订阅或任务；触发条件 |
| 认证与授权 | 身份来源、操作范围及数据权限 |
| 输入/输出 | 关键字段语义、必填/可选、类型/单位/约束 |
| 完成与失败 | 接受成功/业务完成的区别、错误条件、返回/回执 |
| 交互控制 | 超时、重试条件、幂等、顺序、重复与取消（适用时） |
| 兼容与版本 | 版本约束、调用方影响及降级边界 |
| 关联设计 | 需求、模块、流程和状态引用 |

现有接口名与协议可准确保留；目标接口未定时使用设计标识，标明契约方案。源码仅有一个接口壳时不声明链路完整。消息需明确生产者、消费者、消息语义、确认和重投，不用 HTTP 字段结构硬套。

状态机中区分业务状态、订阅/任务运行状态及技术连接状态。未知状态转换不虚构，目标设计中的新增转换与现状差异保留在中间记录。

## 核心流程与异常

流程说明包含场景、需求、参与模块、触发/前置条件、按顺序的交互、状态/数据变化、完成结果及异常。复杂场景使用时序图，分支逻辑使用流程图，跨岗位协作可用泳道图；错误分支不能只画在图里而正文不解释。

流程清单来自需求推导、源码反推或组件材料核对，按 source-and-merge.md 识别需要描述的正常、分支、异常及恢复场景。可借鉴参考材料的段落、步骤表和图文结构，实际角色、规则和交互必须适用于当前范围。跨组件流程统一描述提供方/调用方、状态及数据交接，不能依靠“参见另一个组件文档”补全。

| 异常场景 | 检测/控制位置 | 数据/状态影响 | 回滚/重试/补偿 | 对用户或调用方反馈 | 可验证结果 |
| --- | --- | --- | --- | --- | --- |

按实际适用性覆盖越权、非法参数、无数据、重复提交、并发修改、超时、依赖失败、消息重投及部分成功。重试需要限制与幂等依据；“事务”不能自动覆盖外部系统副作用。没有恢复机制时明确现状缺口或目标方案，不编造已实现能力。

## 最终校审

需求、模块、接口、流程、数据和状态的编号与语义一致，接口两侧契约匹配。权限、时间窗、统计单位及失败反馈与需求一致；目标新增设计有机制与验证场景。核心正常及异常场景可以端到端解释，不依赖打开中间文档。

最终正文不含源码依据、可信度、扫描日志及来源拼接；正常需求引用、真实接口和必要技术名词保留。总体方案的变化有明确决定；概要深度没有被类/字段清单淹没。

各组件文档的模块职责与关键流程均有纳入/合并/排除记录；接口两侧及跨组件流程衔接已核对，参考样式和术语统一。同名异义没有被误合并，不同运行/部署范围没有被强行抹平。只有需求时机制标明目标口径，只有源码时不伪造需求批准或目标方案。

完成条件：开发者能理解协作和契约，测试者能设计关键场景，维护者能评估变更影响，正文与全部图表一致。
