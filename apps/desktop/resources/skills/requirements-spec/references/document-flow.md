# 中间需求与完整需求文档

## 输出位置与命名

允许分别指定中间文档目录、最终文档目录，以及每份文档的文件名或完整路径；明确的逐文件路径优先于阶段目录，阶段目录优先于共同目录，共同目录优先于默认值。相对路径以分析对象的项目根目录解析，绝对路径直接使用；项目根目录确实无法确定且影响输出位置时再询问，不以技能所在目录代替目标项目。

未指定目录时，中间文档与最终文档均保存到目标项目的 `docs/Requirements/`。未指定文件名时采用：

| 阶段 | 文档 | 默认文件名 |
| --- | --- | --- |
| 中间 | 从作为内容依据的参考材料提取并适配的需求 | 参考需求文档.md |
| 中间 | 从实际源码反推的需求 | 源码反推需求文档.md |
| 中间 | 从项目说明、docs、ADR 等生成的需求 | 根据项目文档生成的需求.md |
| 最终 | 融合后的完整需求规格 | XX-需求规格说明书.md |

XX 使用已知项目名称；项目名称未知时使用“需求规格说明书”，不把 XX 当作实际文件名。中间文档和最终文档均为 UTF-8 Markdown（.md），输出路径使用 .md 扩展名。另需 Word 时，将已定稿 Markdown 交给独立的 markdown-to-docx 技能。

仅为实际使用的内容来源生成中间文档；缺少某类来源或参考材料仅作版式模板时说明该分支未生成，不制作空壳，不扩展未授权分析范围。多份同类输入合为该类中间文档，来源定位保留在内部条目中。输入参考材料与“参考需求文档”这一生成成果不同，不能覆盖原输入。已有成果先复用和更新；若指定路径与原输入、其他阶段成果或无关文件冲突，使用区分名称或明确解决路径，避免覆盖。

用户仅要求中间提取或仅要求融合已有中间成果时执行相应阶段，不强制重复扫描。源码 L1 中间成果为功能清单，不能据此冒称完整详细需求已经提取；完整规格仍需满足选定范围所需深度。

## 中间文档

每份中间文档包含分析范围、来源快照、按模块整理的需求、规则/接口/数据等适用内容、证据缺口及输入映射，可用附录承载分析记录。内容使用业务语言，仍可体现以下字段：

- **需求可信度**：已确认 / 合理推断 / 待确认，并明确所确认的是当前实现还是目标要求。
- **源码依据**：实际文件路径、符号和准确代码位置，仅源码证据适用时填写。
- 文档依据、参考适用性、实现状态、分类理由、冲突及分析说明。

按 source-extraction.md 的证据规则记录，不虚构证据或为非源码分支硬填源码依据。中间需求编号可分别管理，必须记录到最终编号的映射。相关来源变化时更新受影响中间文档，再同步最终内容。

## 最终文档的一体化融合

以全部适用中间成果构建统一需求池，再按业务目标组织一份完整文档：

1. 建立一套项目概述、范围、术语、角色、模块划分和章节结构，保留必要版本/场景差异。
2. 对同义及重叠内容逐项合并，互补流程、限制、异常、数据和验收融入对应字段；冲突先按有效决定解决，不把互斥要求拼成一句。
3. 统一最终编号及文风，原中间编号只进入映射记录。共用规则一处定义，各模块有效引用，重建跨模块完整流程和图表。
4. 删除“需求可信度”“源码依据”“文档依据”“来源索引”等分析字段，以及来源章节、源文件位置、追溯矩阵、分析快照、合并过程和来源措辞；同时检查正文、表格、图题、脚注及附录。最终文档不出现“从源码反推”“参考文档指出”“项目文档生成”等编制叙述。
5. 保留业务分类、适用条件、权限、状态、有效限制、异常与验收边界；已选择保留的待确认业务问题仍保留。删除证据痕迹不等于删除真实缺口、抹平现状/目标差异或把推断升级为事实。

最终内容必须能作为独立的完整规格阅读；不能保留三份概述、多个术语表、各来源自己的章节/编号，也不能依赖“见某中间文档”才能理解业务规则。覆盖完整是指当前项目约定范围，不表示所有产品能力或未分析范围均已纳入。

完成条件：适用中间文档均有文件和范围，输入到最终需求的映射完整；最终正文结构、术语、规则及编号统一，无来源拼接痕迹，无需求可信度或证据字段，必要业务内容和人工选择未在清理中丢失。
