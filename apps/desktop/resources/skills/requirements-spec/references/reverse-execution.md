# 源码反推执行分支

依据用户提供的 [源码反推原提示词](reverse-requirements.md) 整理。原文保留用于核对；本文件负责分析执行，SKILL.md 负责文档目标、多来源融合、人工选择与最终交付，spec-template.md 负责正式规格结构，output-formats.md 负责格式制作。

## 深度与范围

用户指定 L1/L2/L3 时沿用，未指定默认 L2；只分析指定范围及必要依赖。先扫描路由、菜单、页面、模块和主要接口建立功能地图，再逐功能深入。大型项目分批分析，复用证据，列出已分析、未分析及不可达分支，不以规模大为由跳过目标深度所需业务规则。

### L1：功能清单

定位业务模块、功能、子功能、用户操作、实际入口及主要实现。每项记录稳定编号、名称、业务描述、主要操作、入口、实现状态与证据位置，形成模块关系和覆盖清单。判断已实现、部分实现或待确认时核对主要实现，区分模拟数据、界面占位及未接后端。

不要求逐项追踪完整调用链。正式成果为功能清单，不套完整用例表，不宣称详细规格或业务验收已完成。

### L2：需求规格

复用 L1 功能地图，追踪主要规则和流程：业务目的、真实角色、触发及前置条件、用户动作/系统响应、结果与后置状态、权限、状态变化、校验、数值及时间限制、筛选、重复操作和异常处理。

提取业务对象、关键字段含义、必填条件、取值范围、关联及有证据的生命周期。核对前后端和数据层的规则一致性、入口与权限、显示与处理、不可达分支。对多步和状态变化生成必要的 Mermaid 业务流程图或状态图，表达业务判断而非函数调用。

功能、规则、数据、接口、可确认的非功能要求及验收边界整理到源码中间需求文档；需求可信度、源码依据、实现状态和疑似问题可保留在相应字段或附录。融合到最终文档时采用正式模板，执行 document-flow.md 的分析痕迹清理规则。

### L3：深度业务还原

保留 L2 业务成果，针对重要业务操作追踪实际存在的完整路径：操作入口、界面/状态管理、请求、接口、服务、数据访问/存储、异步事件或外部系统、返回与界面更新。记录关键文件及符号、调用关系、输入输出、业务判断、数据修改与异常位置，不强行套用不存在的层级。

补充跨模块协作、状态转换触发者/条件/副作用/撤销与终态、数据产生/转换/更新/删除/缓存及外部流动。检查并发、重复提交、越权、超时重试、事务回滚、部分成功、外部失败及一致性。仅记录能证明的行为，未知状态机标出已发现部分。

建立需求—规则—入口—接口—核心实现—数据—测试追溯矩阵，测试不存在时记录缺口。补充实现差异、异常边界、变更的直接/间接依赖、受影响数据及建议验证场景，区分确认依赖与潜在影响。

## 证据与只读边界

结合实际项目检查交互、路由、API、服务、数据持久化、权限状态、配置常量、测试及文档；文件名、函数名和注释只作检索线索。重要结论按已确认、合理推断、待确认记录。读取测试与运行测试分别报告，代码或测试证据不等于运行环境验证。

将实现还原为业务语言；疑似 Bug、硬编码技术限制、过期注释、占位按钮、隐藏/未启用功能记录事实、影响及启用边界，不自动当成正确业务意图。源码证明当前实现；目标要求按 SKILL.md 的文档目标规则处理。

只读取源码、配置、测试及文档，生成分析文档。必要验证使用安全静态分析或无业务副作用的测试；不修改业务代码、数据库及真实数据，不执行具有副作用的业务操作，不自动修复发现的问题。

## 成果与复用

先检查已有分析及其快照，核实受影响内容，保持需求编号稳定，升级时补缺，不无意义重扫或覆盖有效内容。

默认生成一份“源码反推需求文档”作为中间成果，路径、名称及格式按 [document-flow.md](document-flow.md) 执行，保留所选层次需要的证据字段。低层次内容融入所选层次，不因 L2/L3 自动复制全部层次文件。用户明确指定 L1-function-inventory、L2-requirements-spec 或 L3-business-traceability 等名称时按其指定值保存，不另行套用原提示词的默认目录。完成中间文档后与其他来源融合生成最终文档；仅要求源码中间成果时不强制生成最终文档。

完成条件：源码中间文档已保存，所选深度的范围、功能、规则和证据已记录，未知及未覆盖范围明确，结果进入统一需求池；汇报实际层次、覆盖模块、去重后的功能/规则数量与主要缺口。L1 转清单校审，L2/L3 按请求转最终需求编制。
