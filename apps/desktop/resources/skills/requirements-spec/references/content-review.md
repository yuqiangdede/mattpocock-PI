# 内容校审和读者检查

方法来源：[Anthropic doc-coauthoring](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md)。

此处按需求规格书适配 Context Gathering、Refinement & Structure、Reader Testing 三阶段；不是原文全文复制，也不依赖 Claude 专有工具。用户要求使用上游原 Skill 时读取当前版本。它负责内容校审，不生成 Word 文件。

## 上下文整理

整理项目、受众、模板、范围、裁剪及用户已作的选择。已有文档直接作为输入，不重复已结束的访谈。核对可选参考文档是否作为内容来源或样式模板，避免误用示例为项目事实。

核对文档目标与源码分析深度分别明确，来源版本和分析快照可定位。As-Is 描述事实，To-Be 描述有效目标要求，差异分析可区分两者。L1 按功能清单范围校审，不套详细用例完整性标准，也不宣称详细规格完成。

完成条件：关键概念、适用范围和人工选择均明确；真实缺口已按用户选择保留或形成方案。

## 结构迭代

逐项检查：
- 每个输入功能与增量裁剪条目都有归属。
- 实际使用的三类来源分别有中间需求文档，路径和文件名符合指定值或默认目录；没有仅用临时笔记代替中间成果，也没有覆盖原参考输入。
- 参考需求、源码推导需求和 docs/ADR 需求已按 SKILL.md 的统一需求池规则处理，输入映射完整，重复已合并，互补规则和有效验收条件无遗漏。
- 需求目录与正文编号一致；功能需求按业务模块组织，其他类型按模板组织并有效引用，没有按材料来源分开粘贴，也没有同一业务的重复用例。
- 需求名称与功能说明体现用户场景、待解决问题、业务目标和产品能力；需求边界按独立业务目标确定，组件实现细节仅在操作、约束或验收需要时保留。
- 入口、权限、前后状态、流程与验收一致。
- 取消、幂等、并发、无数据、无权限及依赖失败按适用性覆盖。
- 统计单位、公式、时间窗、时区和限制可验证。
- 裁剪同步修改依赖入口、工具、通知、统计和验收。
- 业务分类有认可基准与对照依据；缺少依据不强行归类。材料来源、业务分类、实现状态、可信度及验收结论分别记录。
- 项目文档的有效要求与提议/废弃方案分开；内容参考均有适用性判断及处理去向。
- 当前实现与目标要求的冲突未被简单合并抹平；关键缺口有针对性决定，最可能方案未补造 As-Is 事实。
- 功能用例、共用规则、数据、接口和非功能要求采用适用字段，跨类型引用有效，共用规则不重复。硬性指标含单位及测量条件。
- 复用成果已核对输入版本和本地变化；覆盖及数量与声明的范围、唯一编号和计数口径一致。
- Mermaid 图与正文流程、状态和规则一致，源码及已有预览保留中文、判断、分支与状态含义。
- 产品整体能力没有混入项目范围，原型不成为业务实现证明。
- 正式文风清理不删除真实边界；待确认保留策略没有被擅自改变。
- 最终文档只有一套概述、范围、术语、角色、编号和章节结构，语气及详略一致，跨模块流程和引用完整；没有按来源排列的大段拼接、重复规则、重复图表或中间编号残留。
- 最终正文、表格、脚注、图题及附录中不存在需求可信度、源码依据、证据路径、来源索引、追溯矩阵及编制叙述；这些保留在中间文档或辅助笔记。清理未删去有效约束、例外或业务缺口。

按用户反馈局部编辑文件，避免反复重印或重做已认可内容。Markdown 整理不扩展功能、变更硬性指标或忽略失败边界。

完成条件：覆盖表全部有归属，读过所选层次的全部功能/需求和规则，无跨章节冲突；未解决的关键问题仍有明确处理状态。

## 独立读者检查

生成 5～10 个符合受众角色的问题，例如：
- 从哪里进入，需要哪些权限和配置？
- 操作后什么数据改变，哪些条件不能执行？
- 重投、断线或数据库失败时怎么办？
- 统计单位和计算公式是什么？
- 哪些能力被裁剪，哪些仅保存参数？
- 硬性上限是什么？
- 接口成功是否等于最终业务或物理执行完成？

环境支持且当前授权允许独立子代理时，仅提供文档与问题进行读者测试，不传作者希望的答案。否则按读者视角自行检查，不能冒称独立代理测试；也不必强制用户另开会话。

修复有依据的问题，复核受影响用例。保留模式允许读者明确识别尚未确定的内容；最可能方案模式要求业务规则可独立理解。

完成条件：读者可仅凭正文回答关键问题，或从范围与待确认说明得知边界。自动校审不表示客户确认、代码测试通过或现场验收。

增加整体阅读检查：读者无需打开任何中间文档即可理解最终业务规格；各章节衔接自然，不能从术语、编号、文风或重复内容看出来自多份材料的拼贴。发现差异时回到统一内容基准修订，而非仅修饰段首连接词。
