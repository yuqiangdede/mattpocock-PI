# 标准结构与用例字段

## 章节结构

用户格式优先；无模板采用以下结构，可按实际内容调整，避免空章节。

此结构用于最终文档；中间文档的证据字段及路径规则见 [document-flow.md](document-flow.md)。最终正文从统一需求池重新编写，不拼接中间文件的章节、概述或术语表。

1. 产品概述：产品定位、产品范围、编写目的、术语、描述约定。
2. 总体描述：业务目标、角色、项目范围、裁剪、环境及依赖。
3. 功能需求：目录，按业务模块分组的具体用例；各来源融合后的需求并列编排，基线、定制改动和新增功能体现为用例属性。
4. 外部接口需求：方向、数据、动作、错误及协议边界。
5. 数据与业务规则：状态、单位、公式、唯一性及生命周期。
6. 非功能需求：性能、安全、故障隔离、兼容、审计、留存。
7. 验收要求：范围、场景和关键边界。
8. 待确认清单：仅当人工选择保留时包含。

文档属性只填已知项目、版本、日期、范围和文档目标（当前系统需求/目标交付需求/差异分析）；不编造作者、批准或合同信息。整体产品范围与当前项目详细需求分别表述。附图表示整体能力时说明哪些纳入项目。L1 使用模块总览、功能层级、功能清单、关系、状态及覆盖边界，跳过以下详细用例结构。

## 统一用例表格

以下右栏是编制要求，不得原样作为未填写的交付内容。

| 项目 | 描述要求 |
| --- | --- |
| 需求编号 | 唯一且稳定，沿用用户或现有项目编号 |
| 需求名称 | 用户目标或产品提供的独立业务能力，避免以组件或类名命名 |
| 需求业务分类 | 基线 / 有定制改动 / 全新定制功能；按 SKILL.md 的基准证据规则判定，缺乏依据时分类待确认，推断口径遵循人工选择 |
| 功能说明 | 用户在业务场景中遇到的问题、需要解决的目标，以及产品提供的能力与结果 |
| 优先级 | 高 / 中 / 低，已有明确优先级优先 |
| 功能入口 | 菜单/按钮路径，或消息、接口、任务触发源 |
| 部件说明 | 按需说明用户可见的布局、字段、列表、弹窗、按钮、图表；只保留理解操作或验收所需的细节，有图时关联图号，不列内部组件职责 |
| 参与者 | 业务岗位、授权账号或外部系统 |
| 前置条件 | 权限、配置、数据及业务状态 |
| 后置条件 | 成功后的状态、数据、通知和结果；只读功能说明不改变数据 |
| 正常过程 | N0010 等描述操作和响应，多场景可用 N1/N2 |
| 可选过程 | A0010 等描述分支、取消、替代或恢复；不存在写无 |
| 异常过程 | E0010 等说明失败条件、提示、重试、保留或回滚 |
| 特殊需求 | 专属性能、安全、兼容、实时要求或引用共用规则 |
| 附加说明 | 单位、公式、数据来源、限制和业务边界 |
| 验收要点 | 可观察、可验证的正常及边界结果 |

Markdown 表格中多步骤以 <br> 分隔，段落内容保留完整。业务协议字段可在需要时保留，代码类名和源码位置不进入业务入口。

最终用例表不包含“需求可信度”“源码依据”“文档依据”等分析字段；中间成果允许增加这些字段。可信度字段与按人工选择保留的待确认业务问题分别处理，移除字段时不删除业务缺口。

## 其他需求类型

用户编号优先；无既有规则时功能用 FR、共用规则用 BR、数据用 DR、接口用 IR、非功能用 NFR 前缀，编号全局唯一稳定。编号拆分、合并时在工作笔记记录旧新映射；删除编号不重新分配。

| 类型 | 最小描述字段 |
| --- | --- |
| 共用业务规则 | 编号、名称、适用范围、触发条件、规则及例外、关联需求、验证要点 |
| 数据需求 | 编号、业务对象、字段含义、必填及取值约束、关系/唯一性、状态或生命周期、关联需求、验证要点 |
| 外部接口需求 | 编号、对接对象及方向、触发、输入/输出、授权、协议及错误边界、超时/重试/幂等（适用时）、关联需求、验证要点 |
| 非功能需求 | 编号、质量目标、适用范围、指标及单位、测量条件/负载/环境、验证方法、关联需求 |

业务分类按同一基准规则判定，可作为各类型的属性。没有证据的字段按待确认策略处理；确实不适用的字段说明不适用及理由，不虚构用户步骤。共用规则只保留一处权威定义，在用例中引用编号；局部例外明确适用范围。非功能验收条件与实际测试结果分开，不能凭运行配置推定性能达标。

## 差异分析

在统一需求编号下记录当前实现、目标要求、差异、业务影响及处理决定，可增加差异表或在相应用例中并列呈现；不因现状与目标不同就拆成两个重复功能。当前行为无法证实时写明未知，目标缺少有效依据时保留缺口。As-Is 正文不混入建议目标；建议经用户要求另列。

## 两种待确认模式

**保留模式**：相关字段使用“待确认：…”说明真实缺口，末尾列编号、问题、影响需求及可选方案。正式措辞仍去掉“拟定”“源码推导”等编制痕迹。没有缺口的字段不滥用待确认。

**最可能方案模式**：按 SKILL.md 的普通缺口、关键决策与 As-Is 事实边界规则处理。普通问题形成明确方案，已作明确决定的关键问题按决定编写；已解决的问题删除待确认标记。仍无决定的关键问题不得用统一偏好掩盖，也不能为了去掉标记而删除整个需求。工作笔记保留假设、理由和证据状态。

## 工作笔记

按 [source-extraction.md](source-extraction.md) 的统一映射表、分析快照及属性记录保存证据、分类依据、覆盖、冲突决策、假设和检查结果，可体现于中间文档。最终正文只保留相应文档目标需要的业务规格；其他辅助笔记默认不交付。

## 容易混淆的边界

- 图片数、子事件数、聚合预警数、设备数不能混用；多图不自动增加事件量。
- 人员编码与登录账号编码不是同一概念，授权和负责人映射需明确。
- 资源展示、事件查询、预警生成、自动联动是不同能力；裁剪时逐项处理。
- “无须输入 KEY”与“KEY 必填”按有效增量修订统一，异常过程与验收同步调整。
- 参考文档的“无法测试”不是业务限制，应转换为明确条件与验收方法；实际测试证据另行记录。
