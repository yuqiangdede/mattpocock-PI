## 2. 最重要的升级方法

首次直接按 Git 历史合并时，双方存在多个合并基点，大量已经存在的文件被误判为双方新增，产生许多 `add/add` 冲突。改为以官方 `v0.16.0` 明确指定三方合并基线后，首次冲突收敛到约 45 个文件，主要涉及版本、文档、本地化和运行时接口。

后续升级必须以 `packages/shared/src/upstream.ts` 记录的官方提交为基线：

```text
已接入的官方提交 + 当前定制代码 + 新官方稳定标签
                    ↓
           显式基线的三方增量预览
                    ↓
      无冲突：应用、验证、交付；有冲突：停止并人工处理
```

不要仅凭共同祖先、提交数量或文件版本号判断更新量，也不要整目录覆盖、默认整文件选择官方或本地。历史整合可能改变 Git 的共同祖先，固定的已接入基线仍能明确说明本次究竟继承了哪些官方增量。

## 3. 定制如何与官方保持分离

- `packages/shared/src/upstream.ts`：官方源码版本和提交；不是定制版发布版本。
- `packages/shared/src/fork-config.json`：显示名称、定制仓库、官方仓库和手动更新策略。`protocol.ts` 保留兼容导出。
- `apps/desktop/electron/main/version-sources.ts`：分别比较官方、Matt 技能和定制版的来源；定制版版本较高不能掩盖官方更新。
- Matt 快捷入口、草稿插入和工作流功能保留在各自模块，通过 Composer、IPC、工作面板和 Host 的少量接入位置连接官方实现。
- 不为 Matt 功能复制或改写 Agent Runtime 的提供商、OAuth、压缩和推理核心。通过官方模块的接口接入，并用回归检查兼容性。

工程工作流仍接触 Host 数据库、RPC 和共享类型，尚未完全插件化。原版大幅调整这些接口时仍需要适配，不能承诺每次零冲突。保留 `APP_NAME`、appId 和存储身份的兼容性，避免改变显示名称时让已有数据看起来消失。

## 4. 本次发现的 Windows 问题

| 症状 | 根因 | 保留的修复或验证方法 |
| --- | --- | --- |
| 项目技能禁用状态迁移后失效，冲突键没有被拒绝 | 迁移生成的路径格式与能力状态 JSON 键的规范化格式不一致 | 重写后使用 `normalize_project_path`；验证状态保留与规范化后的键冲突 |
| 项目记忆迁移后读到空内容 | 原本使用正斜杠的项目/记忆身份被改成混合分隔符，键查找失效 | `Roots.remap` 保留原路径格式；重开 Host 后实际读取项目记忆 |
| 冷启动迁移报 `EBUSY`，随后弹窗等待导致测试超时 | Electron ready 时默认 Chromium profile 已打开源目录的 LevelDB `LOCK` | ready 前设置独立的维护 `sessionData`；维护 UI 继续使用非持久分区。没有通过忽略数据库文件或放松校验掩盖锁问题 |
| 模型目录夹具加载失败 | Windows 文件 URL 的 `.pathname` 不是原生文件路径 | 文件读写使用 `fileURLToPath` |
| 隐藏窗口的设置测试超时 | 等待的 `requestAnimationFrame` 被暂停 | 夹具等待任务队列，继续逐项验证真实 DOM、IPC、失败恢复与中文界面 |
| 打包测试错误继承父目录依赖 | 夹具放在项目缓存内，模块解析可以找到仓库的 `node_modules` | 子进程解析守卫禁止依赖越出夹具；验证实际打包输出及虚拟模块加载 |
| Native Pi 消息被误判为重复 | 全文件文本匹配把项目指令中的同名文字也计入消息 | 解析持久化记录，仅计数对应角色和内容，并检查分支与消息 ID |
| 并发测试超时或 worker 异常退出 | 大型工作区测试资源竞争及测试进程稳定性问题 | 模块串行、Vitest worker 上限、桌面测试受限并发、结构化报告；不放宽断言、不忽略未处理错误 |
| 文件符号链接报 `EPERM` | 当前 Windows 进程缺少文件链接权限 | 明确跳过相关文件链接场景；目录 junction 继续实测；POSIX 权限位不冒充 Windows ACL 验收 |
| 更新 Host 二进制时报拒绝访问 | 同一二进制仍被本轮测试进程占用 | 等待所属测试退出再构建，并检查失败退出码；不能继续用旧二进制验证新修复，也不能停止用户已有服务 |

本次冷迁移实际验证了复制校验、离线 Rust 重定位、重开 Host、附件/队列/项目记忆/插件/设置/测试凭据、源备份保留、缓存清理及 Chromium 状态。源码修复不能只凭路径字符串相似或服务健康检查宣称完成。

## 5. 可复用的升级步骤

1. 查看当前主分支、远程、未提交改动、官方标签，以及 `upstream.ts`；先 fetch，保留用户状态。先确认基线检查结果，区分原有失败和升级新增失败。
2. 在最新 `origin/main` 的独立更新分支/工作树中操作。不要在脏主目录直接应用更新。
3. 指定真实稳定版本，先预览，再应用。使用 `refs/tags/upstream/v<版本>` 命名空间，显式抓取并核对旧基线标签；新克隆不一定已经包含基线提交对象。
4. 出现冲突时阅读报告，按功能检查双方意图；同时保留定制身份、工作流数据和官方修复。人工处理后同步基线元数据，再验证。
5. 用 frozen lockfile 初始化依赖；优先复用兼容下载缓存，mutable 状态留在工作树。超过 100 MB 的下载先检查 `D:\cache`，运行依赖不以该缓存为固定路径。
6. 先运行目标检查复现/修复问题，再运行完整门禁。检查命令退出码，构建失败时不能继续宣称后面的测试用了新代码。
7. 提交准确的候选；确认包含最新 `origin/main`，再推送并创建 PR。检查 GitHub 合并候选的 tree 是否与已验证提交一致；不同则验证差异。
8. 获得交付授权后合并、同步本地 main、保留本地修改并保存证据。Git 合并成功与打包、签名、发布、运行中应用升级是不同结果。

具体命令及初始化/启动入口见[操作手册](upstream-updates.md)。`0.16.2` 仅作为命令形式示例，执行时必须核对官方实际存在的稳定标签。

## 6. 入口的真实保证

| 入口 | 保证与限制 |
| --- | --- |
| `pnpm upstream:check --version <版本>` | 使用提交中的源码生成预览；抓取指定官方标签并检查版本/基线一致性，报告和补丁写入项目内缓存 |
| 加 `--apply` | 要求干净的专用分支；拒绝 main/master、脏工作树、降级、标签不一致和冲突；应用候选并更新官方基线记录 |
| `pnpm upstream:verify` | 顺序执行 22 项门禁，失败即停止；结果为 `cache/upstream-validation/results.json`，具体错误看对应日志 |
| GitHub Sync PI upstream | 人工指定稳定版本，只生成预览和报告；不镜像官方 main、不强推、不自动合并 |

预览主要针对已提交的 `HEAD`，不替代对未提交内容的审阅。`--apply` 成功和元数据变更只表示产生了候选，不表示已经完成验收。源码入口不会自动提交、推送或发布。

## 8. 主目录同步和清理经验

本次主目录有用户修改过的 `AGENTS.md`、锁文件和未跟踪文件。同步前保存了原文件、锁文件补丁及哈希；只临时保存影响 fast-forward 的锁文件，再恢复。没有覆盖其他用户文件。

本地备份在 `cache/main-sync-backup-0.16.1/`。仅在确认自己的保存记录已恢复后清理自己的 stash，不能操作其他人的 stash。测试结束只停止本轮启动的进程；本次递归清理被自动审批拦截，因此保留了工作树和缓存，不绕过拦截、不把它当作源码交付失败。
